# 博客写作 Agent 规则

当前目录是写作目录。读取 `1.txt` 获取用户提供的思路和素材；不要读取或写入其他草稿，不要把 `AGENTS.md` 写入博客。

## 文章格式

在当前目录创建 Markdown 文件。文件名只能使用英文小写、数字和连字符。文件开头必须是：

```markdown
---
title: "文章标题"
date: YYYY-MM-DD HH:MM:SS +0800
description: "一句话摘要"
tags: [技术, 随笔]
---
```

- `title`、`date`、`description` 必填；不要添加无用字段或重复标题、日期、摘要。
- `date` 使用文章实际写作或发布时间，时区固定为 `Asia/Shanghai`（`+0800`）。用户未指定时读取当前系统时间，不得使用示例中的占位时间。
- `tags` 选择 1–3 个，不自造同义或英文标签。可选：`技术、编程、软件、硬件、互联网、人工智能、数据、网络安全、开源、产品、设计、创业、商业、职场、管理、教育、学习、阅读、写作、语言、心理、健康、医疗、运动、体育、音乐、电影、游戏、动漫、摄影、旅行、美食、食品、生活、家庭、情感、人物、故事、历史、文化、艺术、社会、政治、经济、金融、投资、法律、环境、科学、未来、随笔、其他`。没有合适标签时使用 `其他`。

## 写作规则

- 直接写结论、依据、机制、步骤和限制。默认读者了解常见概念，不解释 Agent、SDK、API 等基础定义。
- 删除背景铺垫、常识、宣传语和重复结论。
- 优先写作者的判断：选择理由、解决的问题、代价、适用边界和验证方法。
- 句子短，信息密度高
- 删除脱离主题的“正确的废话”
- 禁止使用空泛形容词和说教式、科普式套话。避免“因为……所以……”“我们不要……应该……”“大家都觉得……其实……应该……”等对比和劝导句式；直接写结果。
- 不得编造事实；
- 不为完整性扩写无关内容。
- 文章内容最终是需要作为agent使用的提示词, 请保证内容围绕主题, 删除脱离主题内容

## 资料与资源

- 将 `1.txt` 中的口语和片段改写为明确观点、论据和结论，不保留写作过程表达。
- 用户内容不足时可以补充资料，但必须查证。变化中的数据注明时间；外部事实在文末增加“参考资料”和可靠来源链接。没有可靠来源时不得写成确定事实。
- 独立的方括号是待检索占位符，例如 `{出生人口信息}`；查证后替换。
- 资源放在当前目录的 `asset/`，发布时复制到仓库 `asset/`。引用格式：`![图片](/asset/example.jpg)`、`[下载文件](/asset/example.zip)`。
- 资源文件名只能使用英文、数字、连字符或下划线；引用前确认文件存在。除非用户明确要求，不执行资源中的 JavaScript。

## 发布博客

只有用户明确说“上传博客”“发布文章”或“提交到 GitHub”时才执行发布；写作、修改、润色不执行 Git 操作。

目标仓库：`/Volumes/ActiveBackupforBusiness/personal/feiminjian/work/git/minchieh-fay.github.io`

发布步骤：

1. 检查仓库 `blog/` 是否存在相同文件名，并读取已有文章的 `title` 检查标题冲突。
2. 未经用户明确要求替换、修改或升级，不覆盖已有文章。文件名或标题冲突时，为新文章重新命名，并同步更新文章内引用。
3. 将最终 `.md` 复制到仓库 `blog/`，将引用的资源复制到仓库 `asset/`。不得复制草稿、临时文件或本 `AGENTS.md`。
4. 检查 front matter、文件名和资源路径；检查仓库已有未提交改动，不覆盖或回退这些改动。
5. 在仓库执行：

```bash
git add blog/ asset/
git commit -m "Add new blog article"
git push origin main
```

GitHub Actions 会自动构建发布，不提交 `dist/`，不手动编译。
