企业 Agent 的关键不只是调用模型，还包括公司私有数据、内部技能和工具的组织方式。围绕这些资源，我整理了四种实现方案。它们分别把能力放在 Wails 桌面应用、Electrobun 桌面应用、服务端和客户端壳中，适用的部署边界也不同。

## 方案一：使用 Wails 集成 Agents SDK 开发桌面应用

使用 Wails 把前端界面和 Go 后端集成成一个桌面应用。前端负责调用 Agents SDK，组织 Agent、工作流、提示词和会话；Go 后端通过 API 为前端提供公司的私有数据、技能、工具以及本地系统能力。Agent 的推理和流程编排在前端完成，涉及权限、文件、数据库或内部服务的操作交给 Go API 执行。

这是一种“前端 Agent 编排，Go 后端提供能力”的分层方案。Agents SDK 适合表达多步骤工作流，Wails 负责把桌面应用的界面和本地能力连接起来，Go 后端则集中处理数据访问、工具调用和权限校验。私有业务能力不需要全部写进某个 Agent，而是通过 API 暴露为可复用的后端能力，多个 Agent 可以共享同一套接口。

方案的边界也很明确：前端需要维护 Agents SDK 的运行环境和会话状态，Go API 需要设计稳定的参数、返回值和权限模型。API 密钥、敏感数据和高权限操作不应仅依赖前端控制；涉及公司数据的调用应由 Go 后端再次校验身份、参数和操作范围。适合需要桌面交互、本地资源访问，同时又希望用 Agents SDK 编排业务流程的场景。

## 方案二：使用 Electrobun 开发本地 Agent 应用

使用 Electrobun 开发一个运行在用户设备上的桌面应用。Agent、提示词、工作流和工具调用全部在 Bun 端完成，应用界面负责交互和状态展示。Bun 端可以直接组织公司的 skills、bin 和 data，并调用本地文件、命令和网络资源，适合需要把 Agent 执行环境放在员工电脑上的场景。

这种方案把 Agent 和工具运行时统一放在 Bun 端，前端与执行逻辑之间的边界较小，适合快速组合本地能力。公司的 skills、bin 和 data 可以在线同步到客户端，再由 Bun 端加载和执行。代价是需要处理资源版本、设备权限、数据缓存、更新机制和离线状态；工具拥有的本地权限也必须纳入客户端安全管理。

## 方案三：使用 Pi 开发服务端 Web 服务

使用 Pi 开发一个 Web 服务，部署在公司服务器上，也可以封装成容器，放到对外出售的服务器上。用户通过普通浏览器访问服务；服务端负责保存业务能力并处理主要任务，适合需要集中部署和统一管理的场景。

当服务端本身无法访问公网时，可以借助用户笔记本电脑的网络连接 LLM。浏览器启动时需要使用 `--disable-web-security` 模式，以便服务端通过客户端建立访问路径。这个设计依赖浏览器运行参数，部署前必须重点验证兼容性、数据边界和安全风险。

## 方案四：使用轻量浏览器壳连接服务端

方案四与服务端 Web 服务的主体结构基本一致，区别是自行开发一个轻量浏览器壳。用户通过这个客户端访问公司服务器，客户端负责提供服务器借助本地网络访问 LLM 的能力，服务端继续承担业务逻辑和私有数据管理。

相比直接要求用户启动普通浏览器，浏览器壳可以把网络代理、权限控制和启动参数封装起来。用户不需要手动调整浏览器环境，产品形态也更容易统一。代价是需要额外维护客户端壳、自动更新、系统兼容性和本地权限，开发成本高于直接使用浏览器。

## 选择重点

四种方案的主要区别可以归纳为：方案一强调 Wails 中的前端 Agent 编排与 Go API 分层，方案二强调 Electrobun 中的 Bun 本地执行，方案三强调集中式服务，方案四强调对客户端网络能力的封装。选择时应先确认三点：私有数据必须放在哪里，业务工具需要在哪里执行，部署环境能否直接访问 LLM。

如果业务流程固定且需要桌面应用承载，优先评估 Wails；如果 Agent 和工具需要全部在本地 Bun 环境执行，优先评估 Electrobun；如果需要统一部署和多用户访问，优先评估 Pi Web 服务；如果 Web 服务依赖客户端网络且需要降低使用门槛，再考虑轻量浏览器壳。
