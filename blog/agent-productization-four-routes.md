# 进军 Agent 领域，先选对燃料

Agent 产品的技术路线由三项指标决定：任务所需的上下文理解和规则遵循能力、部署成本、用户操作门槛。按部署方式，方案可分为低配置小模型、中等规模离线模型、低速运行大模型和线上大模型四类。

我把模型比作燃料。小模型像低功率燃料，只能推动轻量设备；中等规模模型可以支撑固定流程；线上大模型则足以驱动复杂 Agent。三者都能做产品，但产品形态完全不同。

## Agent 的能力不只取决于参数量

大模型和小模型的差距，至少有一部分体现在对上下文的遵循上。模型运行时接收的上下文包括系统规则、任务目标、历史对话、工具说明和外部资料。系统提示词通常拥有最高约束优先级，Agent 是否能在多轮操作中持续遵守这些规则，直接影响结果是否稳定。

可以把系统提示词理解成家庭规则：回家先洗手、晚上十点前睡觉、未经允许不能拿别人的东西。大模型更有机会在复杂情境下同时记住并执行这些规则，小模型则更容易在上下文变长、任务变复杂后遗漏约束。这不是“聪明”与“笨”的简单差别，而是产品能否把模型放进一个可控工作流的问题。

因此，离线部署的判断标准不能只是“模型成功跑起来了”。还要验证它在实际上下文长度、工具调用、错误恢复和规则冲突下是否仍然可用。只看单轮问答，很容易高估一个模型对 Agent 的支撑能力。

## 路线一：低成本硬件加离线小模型

第一条路线是把成本控制在五千元以内，使用本地硬件运行约 4B 规模的模型。

这种方案的优势很明确：数据不必离开本地，运行成本和网络依赖较低，硬件也容易标准化。但它更适合检索和有限任务，不适合期待它像 Codex 或 Claude Code 一样处理开放式开发工作。

RAG 也不是把文件塞进向量数据库就结束了。数据量增加后，同类内容会互相稀释；不重要的材料可能抢占检索结果；不同时间形成的结论还可能彼此冲突。比如一份资料说“AI 是未来”，另一份资料又说“AI 只是基座，Agent 才是未来”。如果没有时间、来源和优先级管理，检索系统会把矛盾原样交给模型。

所以，小模型离线设备更适合边界清晰的知识查询、设备控制和局部自动化。它的价值在隐私、成本和可部署性，不在于模拟一个全能 Agent。

## 路线二：中等产品支撑固定工作流

第二条路线是做一个约一万元级别的产品，运行 12B 到 30B 左右的离线模型。这类模型的表现足以支撑一般 Agent 和业务流程，但距离复杂的软件工程 Agent 仍有明显差距。

它适合处理输入和输出都相对受控的任务：客服分流、表单填写、设备巡检、资料归档，或者根据用户的 A、B、C、D 选项推进下一步。传统交互中的“请说 1、投诉请说 2、转人工请按 3”，本质上就是这类可验证工作流。

这个阶段的模型像酒精燃料，可以让孔明灯或热气球升起来，但很难让汽车持续行驶。产品仍然能做成，但必须把任务拆细，把提示词、工具权限、失败分支和人工接管设计得足够精确。

我正在尝试把这条路线落到 HAA 产品上。现阶段的判断是：简单操作可以做，关键不在继续堆功能，而在极致优化每一个高频动作。只要任务边界清楚，中等模型也能产生实际价值；一旦让它自由处理长链路、开放式问题，稳定性会迅速下降。

## 路线三：低配置运行大模型

还有一种小硬件方案，成本与路线一接近，但目标不是运行 4B 小模型，而是在有限显存中运行更大规模的模型。开源库 AirLLM 采用分层加载方式，将模型切分成多个部分，在磁盘和显存之间交换：运行到哪一层，就把对应层加载到显存中。项目宣称 4GB 显存可以运行 70B 模型、8GB 显存可以运行 405B 模型，具体可用性仍取决于模型格式、量化方式、磁盘速度和上下文长度。

这种方案用速度换模型规模。模型层需要频繁在磁盘和显存之间交换，生成速度可能只有约 0.5 token/秒，无法满足实时对话和连续操作。它适合另一类任务：准确性比响应速度重要，任务提交后可以等待数小时甚至隔夜。例如，企业每天提交一份合同，系统在本地完成审核，第二天返回风险条款、缺失内容和修改建议。

这条路线的关键不是证明小硬件能运行大模型，而是找到能够接受低速处理的商业场景。合同审核、批量文档分析、历史资料整理等任务不要求即时响应，但要求模型具备更强的理解能力。上线前仍需用目标领域数据测试准确率、漏检率和幻觉率，不能因为模型参数量更大就直接认为结果更可靠。

## 路线四：线上大模型与产品化

第四条路线是使用线上大模型。它的能力更接近汽油，能够驱动复杂 Agent，支持多轮推理、工具协作和开放式任务。

但线上模型的能力并不等于用户可以直接获得的能力。当前优秀 Agent 的安装、账号配置、权限管理和使用方式，本身就是一道门槛。一个熟悉工具的人可能几分钟就能定位并解决现场问题，普通员工却未必能复现同样的过程。问题不一定是员工不愿意使用，而是产品把过多逻辑判断留给了用户。

这条路线有两个方向。

### 方向一：让优秀 Agent 被普通用户用起来

市场上不缺优秀 Agent，缺的是能被普通用户直接使用的产品。一个 Agent 如果要求用户自行安装环境、申请账号、配置模型、设置权限、理解工具调用方式，实际能用起来的只能是少数专业用户。即使底层能力足够强，对大多数人仍然等于不能用，覆盖面可能只有 10%。

这条路线的核心工作，是把专业用户承担的复杂度收回产品内部：提供一键安装和配置，预设模型与权限，隐藏不必要的技术选项，处理错误和升级，并把业务数据、RAG 知识库与 Agent 接通。用户只需要提交任务，产品负责完成剩余步骤。

腾讯是在 OpenClaw 的基础上做面向中国用户的产品化精加工，将其改造成 QClaw。QClaw 的核心仍然是 OpenClaw，主要变化在于安装、配置和使用体验，让中国用户更容易使用这套 Agent。这个例子说明，降低使用门槛不是附加功能，而是通用 Agent 从“专业工具”变成“大众产品”的必要条件。

这条路的难点是持续承担底层变化。模型、权限、接口或数据格式发生变化时，封装层都要同步维护；否则用户很快会重新面对原来的配置门槛。

### 方向二：避开通用 Agent，深挖垂直场景

另一条路是不和通用产品正面竞争，而是选择一个领域，把任务闭环做深。

教育是一个直观例子：家长用手机拍下孩子一个月的错题，系统识别题目、归纳错误类型、生成相似练习，再联动局域网打印机输出题目。这里真正的产品不是“一个会聊天的 AI”，而是从采集、分析、生成到打印的完整流程。

垂直 Agent 的优势在于可以限制输入、工具和评价标准。错题是否识别正确、生成的题目是否对应知识点、打印是否成功，都能被单独验证。场景越具体，越容易建立数据反馈，也越容易判断模型到底有没有创造价值。

## 商业场景必须允许模型犯错

即使使用最强模型，也不能把结果当成百分之百正确。一次任务的准确率如果只有 80%，再经过多次 Agent 串联，整体准确率还会继续下降。黄魏在 2025 年谈到选择自媒体领域时提过类似判断：如果一个环节的准确率只有 80%，经过多次工作流后，最终准确率可能连一半都不到。

因此，商业场景的选择不能只看模型能不能完成任务，还要看模型犯错后会造成什么后果。适合产品化的任务通常满足两个条件之一：错误本身可以容忍，或者后面有程序规则、人工审核和专业人员调试等兜底环节。

教育场景可以对比两种做法。第一种是让 AI 直接批改奥数题。AI 可能在推导步骤、特殊解法或题意判断上批错，这类错误会直接影响孩子的成绩判断，不适合作为完全自动化的结果。第二种是家长用手机拍下孩子这个月所有已经被老师批改过的作业，再让 AI 根据其中的错题生成训练卷。AI 可能识别错题时出现偏差，例如老师的叉号位置偏上，被模型误认为上一道题做错；但生成 50 道题时混入一道孩子本来就会的题，通常不会破坏整个训练过程。这种错误是可容忍的，方案也更适合产品化。

写代码是另一种有兜底的场景。模型可以生成错误代码，但程序员能够通过测试、运行结果和代码审查发现问题并修正。只要验证环节的成本低于人工从头完成任务，模型犯错仍然可以转化为效率收益。

场景选择的核心不是追求模型零错误，而是把错误限制在可接受范围内。应优先选择“错了也不会造成严重后果”的任务，或者选择“错误能被快速发现和修正”的任务。

## 先确定能力边界，再决定模型

四条路线没有绝对的高下：

- 小模型适合本地、低成本、边界清楚的任务。
- 中等模型适合固定流程和有限工具协作。
- 低速运行的大模型适合准确性优先、可以等待的离线任务。
- 线上大模型适合复杂任务，但必须解决成本、权限和使用门槛。

真正值得投入的方向，不是把最强模型塞进所有产品，而是找到模型能力与任务复杂度的交点。模型不够强时，就缩小任务边界；用户不会配置时，就把配置变成产品；通用 Agent 难以形成差异化时，就把一个垂直场景的完整闭环做出来。

Agent 的竞争最终会落到两个问题：模型能否在真实上下文中稳定完成任务，产品能否替用户承担复杂性。先回答这两个问题，再决定买什么硬件、调用哪个模型，路线会清楚得多。
