我想做的不是另一个通用聊天客户端，而是一套可复用的垂直 Agent 桌面应用。

它有一个固定的聊天界面，底层是一组由 Go 实现的本地工具，Agent 的具体流程则按项目替换。换项目时，不必重新开发整套 UI 和工具层，只需要重新组装 agent tree、工具权限和业务 flow。

## 为什么选 Wails

桌面壳需要同时满足三个条件：前端能快速迭代，二进制足够小，并且能直接调用本地能力。

我会选 Wails。它用 Web 技术做界面，用 Go 承担后端逻辑，符合这个项目的分工：聊天 UI、流式输出和交互状态交给 JavaScript，文件系统、进程、网络和集群操作放在 Go 侧。Go 的生态也足以覆盖 SSH、HTTP、进程管理和 Kubernetes 客户端等需求。

相比 Electron，Wails 的主要吸引力是运行时负担更小。Electron 把 Chromium 和 Node.js 一起带进应用，工程体验成熟，但安装包和常驻资源开销通常更高。相比 Tauri，Wails 的优势不在于所有指标都更好，而在于后端直接使用 Go，团队可以减少 Rust 学习和跨语言维护成本。这个选择是工程权衡，不应简化成“Wails 一定比 Tauri 快”或“所有平台都只有几兆”。最终体积仍取决于 WebView、依赖、资源和目标平台。

## 分层方式

可以把应用拆成四层：

1. **桌面壳**：Wails 负责窗口、生命周期、打包和前后端通信。
2. **工具层**：Go 封装文件读写、`ls`、`grep`、`curl`、SSH、Kubernetes 查询等能力。
3. **Agent 适配层**：浏览器中的 JavaScript 将 Go 接口包装成 Agents SDK 可以调用的 tools。
4. **业务流程层**：针对某个项目定义 agent、handoff、检查顺序、输入约束和输出格式。

Agents SDK 适合承载第三层和第四层之间的编排：它支持工具、上下文、流式运行以及 agent 之间的 handoff，并提供 TypeScript 和 Python 实现。桌面应用不必把 SDK 的所有能力都搬到 Go 侧；Go 更适合做受控的执行边界，Agent 只通过明确的工具契约访问它。

例如，工具不应该只暴露一个可以执行任意 Shell 的 `run_command`。更可靠的接口是 `get_cluster_info`、`list_configmaps`、`check_deployment` 这类带参数约束的操作。这样做会牺牲一部分自由度，却能缩小权限范围，让日志、错误处理和测试都有明确对象。

## 垂直 Agent 的价值

通用模型的问题通常不是不会分析，而是缺少稳定的业务上下文。

假设团队的 Kubernetes 集群统一使用 host 网络模式，某些 ConfigMap 必须按照内部约定配置，服务启动还依赖一组固定的外部组件。每次对话都把这些约束重新描述一遍，既浪费上下文，也无法保证模型记住了全部前提。更麻烦的是，描述本身可能过时，而集群中的实际状态才是诊断依据。

垂直 Agent 可以把这些约束固化在流程里：先读取目标集群的事实，再检查网络模式和配置项，随后对照服务依赖关系，最后输出发现的问题、证据和建议动作。用户只需要说：“帮忙检查集群 `xxx` 的配置。”

这里的关键不是给模型塞一篇更长的系统提示词，而是把业务知识转成可执行的检查步骤和工具契约。模型负责选择下一步和组织结果，工具负责读取事实，规则负责判断硬约束。三者职责分开后，结果更容易复现，也更容易定位错误来自数据、规则还是模型判断。

## 复用的边界

“工具层和 UI 可以复用”是可行的；“所有业务都共用一套 Agent 逻辑”则通常会导致抽象过度。

可复用的部分包括桌面窗口、对话记录、流式事件、工具调用展示、凭据管理、日志和基础工具。需要按项目变化的部分包括领域对象、检查规则、handoff 拓扑、工具白名单、审批节点和结果模板。

尤其要把有副作用的动作和只读检查分开。查看配置可以自动执行，修改 ConfigMap、重启 Deployment 或删除资源则应进入显式确认或审批流程。每次工具调用都应记录调用者、参数、返回摘要和目标资源；否则出了问题，聊天记录很难替代真正的审计日志。

还需要考虑上下文的新鲜度。集群状态会变化，静态注入的“知识”不能代替实时查询。流程应优先获取事实，并在结果中区分“工具返回的状态”“规则校验的结论”和“模型提出的推测”。

## 先做什么

第一版不必覆盖所有命令。可以先做一个只读的 Kubernetes 配置检查器：

- Go 侧只提供集群连接、资源读取和少量结构化检查接口；
- JavaScript 侧定义工具 schema、参数校验和流式事件处理；
- Agent flow 固定为收集目标、读取状态、执行检查、汇总证据；
- UI 展示每次工具调用和检查结果，而不是只展示最终自然语言；
- 用一组脱敏的真实故障样本验证误报、漏报和无法连接时的行为。

验证重点不是“能不能聊得像人”，而是同一个集群状态能否得到稳定结论，工具失败时是否会停止编造，以及修改操作是否绝不会绕过确认。通过这组验证后，再把同一套壳扩展到 SSH、日志分析或其他内部运维流程。

这套路线的价值在于积累可复用的执行能力，而不是积累更多聊天页面。通用模型提供推理能力，Go 工具层提供事实和动作边界，业务 flow 提供组织经验。三者组合起来，才有机会让 Agent 真正贴近一个团队的工作方式。
