Agent 产品大致有三种形态：开发式、工作流式和半开放式工作流。它们的主要差异不在于是否使用模型，而在于任务边界由谁定义：用户临时定义、产品预先定义，还是由产品先限定领域，再允许用户在领域内自由表达。

## 一、开发式 Agent：能力宽，使用门槛高

ChatGPT、Codex、Claude Code 等产品属于开发式 Agent。用户面对一个开放输入框，可以让 Agent 处理编程、写作、分析和操作等不同任务。任务范围宽是它的核心价值，也是使用成本的来源。

这种形态要求用户在请求中提供足够的背景、目标、约束和验收标准。普通用户往往只知道“想要什么结果”，不知道哪些信息会影响执行，也不知道如何把需求描述成模型可以稳定执行的指令。结果是：大多数人难以持续用好这类产品，能够熟练使用的人通常已经具备较强的专业能力或任务拆解能力。

开发式 Agent 对模型和上下文也有更高要求。一个会话可能同时包含需求澄清、资料读取、方案选择、工具调用和结果校验。任务越宽泛，模型需要保留的背景越多，错误路径也越难控制。它适合探索性任务和边界不清的工作，不适合作为大规模、标准化业务的唯一入口。

## 二、固定工作流：确定性强，灵活性有限

工作流式 Agent 把复杂工作拆成多个职责明确的小 Agent，每个 Agent 只完成一个确定步骤，把信息收集、条件校验、执行操作和结果返回放进可控节点。Dify 是这类工作流产品的代表，重点在于通过可视化编排连接模型、工具和业务节点。

这种设计降低了单个 Agent 的能力要求。输入格式、执行条件和输出结果都可以预先约束，测试、监控和失败重试更容易实施。对于“办理 100 元套餐”和“办理 200 元套餐”这类选项明确的任务，固定工作流通常比开放对话更稳定。

代价是需求一旦越过预设分支，流程就无法自然承接。例如，用户提出“办理 150 元套餐”，而工作流只配置了 100 元和 200 元两个选项，系统只能拒绝、转人工或等待新增流程。工作流覆盖的场景越窄，确定性越高，但产品处理例外需求的能力越弱。

## 三、半开放式工作流：先限定领域，再开放表达

半开放式工作流把两种形态放在同一个产品中：产品先通过工作流限定任务领域、必要信息和可执行动作；用户进入该领域后，可以像使用开发式 Agent 一样自由描述需求。Agent 在工作流范围内理解意图、补充信息并执行操作，处理过程中还可以在保留上下文的前提下切换到另一个相关工作流。

典型交互可以分成四步：

1. 用户在左侧选择一个明确的工作流，例如 Linux 远程操作。
2. 界面要求用户填写目标服务器、SSH 端口、账号、密码和提权方式等必要信息。
3. 用户在该工作流的对话区域中直接描述任务，例如查询内存，或把本地文件上传到服务器指定目录。
4. Agent 根据当前工作流的上下文执行操作；如果任务需要另一个流程，则带着已有上下文切换，而不是重新开始一轮开放对话。

## 设计重点：把边界放在正确的位置

半开放式工作流的关键不是把所有工作流串起来，而是明确三类边界：

- **输入边界**：哪些信息必须在进入工作流时收集，哪些信息可以在对话中补充。
- **能力边界**：Agent 可以执行哪些动作，哪些请求必须拒绝或转人工。
- **切换边界**：什么条件下允许切换工作流，以及切换时哪些上下文可以继续使用。

输入边界决定稳定性。以 SSH 操作为例，服务器地址、端口和认证方式属于执行前必须确认的信息；“查询内存”属于进入工作流后的自然语言任务。两者混在一个开放输入框中，会增加识别和校验成本。

能力边界决定风险。用户可以自由描述目标，不代表 Agent 可以自由执行任意命令。高风险操作应设置确认步骤、权限限制和结果校验；低风险查询可以直接执行。具体规则需要根据业务环境验证，不能仅凭对话体验判断安全性。

切换边界决定连续性。相关工作流之间可以共享任务目标、用户已经确认的参数和执行结果；不相关工作流不应盲目继承上下文，否则旧任务的信息可能污染新任务。切换时应记录触发原因和传递字段，便于定位错误。

## 结论

开发式 Agent 适合开放探索，固定工作流适合标准化执行，半开放式工作流适合既有明确业务边界、又存在大量自然语言例外的场景。若目标是让更多用户完成真实操作，较合理的产品结构是：用工作流降低输入和执行门槛，用对话承接工作流内部的变化，用权限、确认和校验控制自由度。

这个方向的验证重点有三个：用户能否在首次使用时填对必要信息；工作流能否覆盖主要任务而不频繁打断用户；任务跨流程时上下文是否完整且不产生错误继承。只有这三项同时成立，半开放式工作流才真正兼顾了确定性与灵活性。
