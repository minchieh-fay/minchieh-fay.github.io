我想按 [Wails Vertical Agent](https://minchieh-fay.github.io/blog/wails-vertical-agent/) 的思路做一个 Agent。很快会遇到一个具体问题：前端的 TypeScript 需要调用很多 Go API，而其中一部分调用来自普通业务逻辑，另一部分来自 Agent。两者是否应该使用两套 API？

我的答案是：不应该在 Go 侧区分调用者。API 表达的是应用允许执行的能力，至于调用来自界面按钮、自动化流程还是 Agent，由上层决定。

## Agent 不需要一套特殊的本机 API

Wails 的前端本质上仍然运行在浏览器环境中。浏览器擅长渲染界面和执行受限的脚本，但不能直接读取任意本地文件、执行进程或访问用户的 SSH 环境。这些动作必须由 Go 后端完成，再通过 Wails 暴露给 TypeScript。

因此，一个实用的桌面 Agent 至少会需要几类本机能力：

- 配置文件和应用状态的读写；
- 文件、目录和工作区操作；
- `ssh`、`curl`、`wget` 等外部工具的调用；
- 面向具体工作流的业务能力，例如 Kubernetes、演示文稿或表格处理。

这些能力并不会因为调用者变成 Agent 就改变语义。Agent 需要读取文件时，使用的仍然是文件读取能力；需要访问远程主机时，使用的仍然是 SSH 能力。为 Agent 另做一套 `agentReadFile`、`agentSSH` API，通常只会产生重复的参数校验、错误处理和权限判断。

更合理的分层是：Go 侧提供稳定的能力 API，TypeScript 侧负责把这些能力组合成产品流程，Agent 负责根据任务选择和编排能力。

```text
界面操作 / Agent
          |
       TypeScript
          |
        Wails
          |
          Go API
     file / system / ssh / k8s / ...
```

统一 API 也有一个实际好处：手工操作和 Agent 操作可以复用同一套实现，问题更容易复现。用户通过界面执行一次操作失败后，能够用相同的 API 参数重放 Agent 的调用，而不是面对两条行为不一致的代码路径。

## “能调用”不等于“应该开放”

Go 侧可以调用本机命令，并不意味着应该把任意命令执行能力直接暴露给前端或 Agent。`ssh`、`curl` 和 `wget` 都是有用的业务能力，但它们也会扩大数据泄露、误操作和提示注入的影响范围。

所以 API 的设计重点不是把 Go 函数原样映射给 TypeScript，而是给能力定义明确的边界。例如：

- 文件 API 需要限制工作区、允许的路径和覆盖行为；
- SSH API 需要明确目标主机、凭据来源、超时和输出大小；
- 网络请求需要限制协议、目标范围、重定向和本地网络访问；
- 外部进程需要区分固定参数的业务操作和任意命令执行；
- 高风险动作应该返回可审计的执行记录，并允许用户确认。

这些约束应当位于 Go 能力层，而不是只依赖 Agent 的提示词。提示词可以影响选择，却不能充当安全边界。否则，换一个前端调用路径，或者出现一次不符合预期的模型输出，约束就可能失效。

这也意味着“统一 API”不等于“无差别授权”。调用者可以统一使用同一组能力，但每次调用仍然应该经过参数校验、权限判断和必要的用户确认。

## 用模块拆分 Go API

最初可以把所有方法写进一个 `app.go`：定义 `App` 结构体，然后注册到 Wails，让 TypeScript 调用。这个方案在接口很少时简单直接，但随着功能增加，单文件会同时承担 API 注册、文件操作、系统调用和业务逻辑，阅读和测试都会变得困难。

我倾向于按业务能力拆分目录，每个目录拥有自己的 `app.go`。例如：

```text
backend/
├── app.go
├── file/
│   └── app.go
├── system/
│   └── app.go
├── ssh/
│   └── app.go
├── k8s/
│   └── app.go
├── ppt/
│   └── app.go
└── excel/
    └── app.go
```

这里的 `app.go` 不应该成为所有实现代码的垃圾桶。它更适合作为该模块对外暴露的入口，集中放置 Wails 需要绑定的方法；复杂逻辑可以继续拆到 `service`、`client` 或其他内部文件中。这样做的价值在于模块边界清楚：文件能力的变更不必穿过一个包含上千个方法的总文件。

主目录的 `app.go` 只负责聚合：

```go
type App struct {
	file.App
	system.App
	ssh.App
	k8s.App
	ppt.App
	excel.App
}
```

利用 Go 的嵌入字段，主 `App` 可以把各业务模块的方法统一暴露给 Wails。新增模块时，通常只需要实现模块自身的接口，再在聚合结构中注册。这个结构适合接口数量持续增长的应用，也让模块可以独立编写测试。

## 聚合结构还需要几条纪律

嵌入结构体很方便，但它不是模块治理本身。接口数量达到数百甚至上千时，还需要保持几条纪律。

第一，公开方法应当使用业务对象，而不是把底层命令行参数直接暴露出去。比如 `ssh.Run` 如果只接收一段任意命令，调用者就无法从类型上区分安全的固定操作和高风险的命令执行。可以为常见任务设计结构化请求，并把任意命令能力单独放进更严格的权限路径。

第二，模块之间不要互相调用嵌入后的总 `App`。模块应该依赖明确的接口或内部服务，否则很容易形成循环依赖，最终所有模块又退化成一个隐形的“大对象”。

第三，统一处理错误、超时、取消和日志。尤其是外部进程和网络操作，如果没有超时与输出上限，Agent 的一次调用就可能长时间占用应用，甚至耗尽内存。错误中也不应默认包含凭据、完整环境变量或敏感路径。

第四，给 API 设计版本意识。Agent 会依赖这些方法的名称、参数和返回结构；随意修改字段，比修改普通界面更容易造成隐蔽的行为回归。对高频使用的接口，稳定的请求和响应结构比追求最少代码更重要。

## 我会先实现什么

第一阶段不会从“让 Agent 能执行任意命令”开始，而会先建立几组可验证的窄能力：工作区内的文件读写、受限的进程执行、配置管理，以及带超时和输出限制的 HTTP 请求。每个接口都配套记录调用参数、执行结果和失败原因，再逐步增加 SSH、Kubernetes 等业务模块。

验证重点也不只是“TypeScript 能否调用 Go 方法”，还包括路径逃逸、命令参数注入、超时取消、重复执行、错误恢复和敏感信息泄露。只有这些边界稳定后，Agent 的自动编排才有可靠基础。

最终的目录结构只是表面。真正重要的是把本机能力抽象成有边界、可测试、可审计的业务 API，再让界面和 Agent 共享这套能力。这样，Agent 是应用能力的编排者，而不是一条绕过应用约束的特殊后门。
